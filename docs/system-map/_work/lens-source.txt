LENSES (word for word)
## 3B. The 360 lenses (run every lens over every surface; journeys are lens 1)

Each lens is one helper brief per surface. Each writes findings into `findings.jsonl` with `lens` filled, and a row
per (surface, lens) into `docs/system-map/LENS-GRID.json` {surface, lens, checked_on, items_checked, findings,
evidence[]}. A lens is "checked" only when every item in its checklist below has a line in the evidence.

**Grid set-up (coordinator, once, after A2).**
1. lens-items.json: split each lens and hunt cell at every ";" and sentence end into numbered items
   (L3.1 "every server route and RPC: who can call it", L3.2 ...). An item id never changes.
2. applies.json: for each surface x lens/hunt write yes, or "no: <reason in 10 words>". A "no" cell is filled
   in the grid as "does not apply: <reason>" and costs no helper. He sees the list of "no" cells in the
   Phase A summary.
3. Bundles (one helper reads an area once and answers several lenses): B-sec = lenses 3 + 19;
   B-run = lenses 6 + 15 + hunt 8; B-truth = lenses 2 + 17 + hunt 9; B-alerts = lens 11 + hunts 2 + 3 + 4;
   B-words = lens 10 + hunt 10; B-time = lenses 13 + 20 + hunt 7; B-switch = hunts 1 + 6. Lenses 4, 5, 7, 8,
   9, 12, 14, 16, hunt 5 run alone. Big surfaces run a bundle per AREA (see A2), small ones per surface.
4. A grid row: {surface, area, lens, items: [{item, status: checked | does-not-apply | could-not-check,
   evidence, finding_ids[]}]}. "could-not-check" needs the reason and goes into DEFERRED.md.
merge.mjs fails a lens work item if any of its item ids has no row.

GAP HUNTS (word for word)
## 3D. Gap hunts: what is MISSING, not only what is wrong (his ask, 16 Nov 2026)

His words (16 Nov 2026): "I keep stumbling into these issues and I am afraid there might be hundreds and hundreds of
these gaps hidden in the code. I want that audit to be able to surface all of it."

**Why the map alone misses them.** `readers.json` and `impact.json` trace reads that EXIST. The gaps he keeps hitting
are reads that are MISSING, conditions nobody can see, and features that do not know about each other. Example, 16 Nov:
the gym switched automatic birthday wishes on, but the AI Assistant still said "Birthdays today: write wishes" (the
idea never reads the switch: no line in any map joins them). And the wish never reached Digvijay, because it works
only for members whose app is linked by a proven number, and nothing in the panel shows who is left out.

Run all 10 hunts over every surface. Each is one helper brief per surface (section 0 rules apply). Findings go to
`findings.jsonl` with `lens: "gap-<n>"`; each hunt gets a LENS-GRID row like the 20 lenses. A hunt is "checked" only
when every item it lists has a line of evidence.

1. **Should-read matrix (missing links).** List every setting, switch, plan gate, status and automation (from
   `features.json` + `entities.json`). For EACH one, list every other feature whose result it SHOULD change (the AI
   ideas, Today, counts, badges, reminders, messages, help, exports, the phone app). Then check in code that each of
   those really reads it. A should-read with no read = finding. (Seed pairs: coordinator-only, in the calibration list.)
2. **Hidden conditions (works only if ...).** For every automatic or "on" feature: write ALL conditions for it to
   reach one person (app installed, app linked by proven number, notifications allowed, phone maker rules, plan
   running, data filled in like birthday/phone, feature switch, version). Then check: can the owner SEE, per member,
   who will get it and who will not, and why? If the switch says "on" but some people silently get nothing = finding.
   Count real reach on Crispy Curves (e.g. "birthday wish: on, reaches 1 of 40 members").
   Where reaching the person depends on the phone or the watch itself (phone maker sound, banner and battery rules
   that can change what the app asked for, a paired watch the phone must detect, a version check between phone and
   watch): mark that path "cannot be proven in the cloud, needs a real-phone check" and name what to look at on the
   device.
3. **Did it happen? (proof of every automatic action).** Every automatic send, reminder, push, digest, job: is there
   a record the owner (or HQ) can open that says it went, to whom, when, and why not when it did not? An automatic
   action with no record and no "why not" = finding (S2 when the owner believes it ran).
4. **Two features, one job (overlap and conflict).** Find every pair of features that act on the same people or the
   same event (manual message vs automatic reminder; AI idea vs Today nudge; bell vs Today vs push; desk link vs
   phone proof). Check they agree: no double message, no suggestion to do what the system already did, the same
   count in both places, "done" in one is "done" in the other.
   For every "done", "read" or "seen" mark: find where it is kept (this browser only, this phone only, or the server).
   Every other place that counts or sends the same items (a server push or daily summary, another device, another
   staff member, Today, the bell) must read that same mark; a mark kept in one place while another place still counts
   the same item as waiting = finding.
   Also the case where no mark exists at all: every list or count of items that point at a thing to act on (alerts,
   to-dos, a daily summary). When that thing is handled in its own page (reply sent, request settled, enquiry
   closed), does the item leave the list and the count in every place, server sends included, without anyone
   touching the item itself? An item that cannot learn its thing was handled = finding.
5. **Built vs live (deploy state).** For every feature in `features.json`: is it on main, deployed, behind a switch,
   or waiting for a migration? Compare code on main with what the live panel, HQ, website, phone app (Play version)
   and database really run (check the live version labels, `list_migrations`/catalog, switches). Any feature the
   notes or What's new call live that is not live = finding. Output `docs/system-map/LIVE-STATE.md` (one row per
   feature: main / live panel / live DB / Play app), so he can always see what is really live.
6. **Data a feature needs but nobody fills.** For every field a feature depends on (birthday, phone, check-in
   phone, app link, plan dates, trainer, batch): how many Crispy Curves rows have it filled? Is there a screen
   that asks for it at the right moment? A feature that depends on a field most rows lack = finding.
   For every input box (mobile number, name, date): feed it what a phone keyboard autofill or a paste really puts in
   (country code, spaces, dashes, digits in other scripts) and check that the length limit and the cleaning step
   together keep a valid value; a box that cuts or refuses a real autofill = finding.
7. **Old users, new rules.** Every new flow that fixes something only for NEW installs or NEW members (e.g. the
   phone sign-in shows only on new installs): what happens to existing users? Is there a path for them? None =
   finding.
   And the reverse: every "new since your last version" mark (dots, What's new, update notices, tips): what does a
   brand-new install or a brand-new member see? New marks on things that are not new to them = finding.
8. **Silent fallbacks.** By script first: docs/system-map/_tools/silent.mjs lists every catch block with file:line and three flags:
logs? (calls a log, report or crash function inside), tells_user? (sets an error state, toast or alert
inside), rethrows?. Output _sources/silent.csv. Helpers read ONLY the rows where all three are "no", plus
every fallback value (?? null, || [], ?? 0) that sits in a file named in a journey that writes money,
messages, alerts, sign-in or sync. Everything else is counted in the grid as "filtered by script, N rows,
not read" so the gap is visible. For each: if this path runs, does the user (or owner, or HQ) learn anything? A silent path
   that hides a failed promise = finding.
9. **Same fact, every place.** For each fact a user sees (count of alerts, dues, plan end, birthdays today, members
   using the app): list every place it shows (panel, Today, AI, bell, push, phone app, HQ, export) and compare the
   values on the Crispy Curves data and the ugly data pack. Any difference = finding.
   For every number worked out from dates (not seen for N days, ends in N days, new this week, after a long gap): test
   the edges (day 0, someone who joined today, a plan that starts later, no visit yet, a gap of weeks). A number wrong
   at an edge = finding. For every summary number shown with its own rows (a total, a target, a score): check it is
   worked out from those same rows, and when it is lower than last time the screen says why. A summary that differs
   from its rows, or a drop with no reason shown = finding.
   Open the files that work numbers out (engine, logic, lib, store), not only the screens that draw them. For each
   number a screen shows above or beside its rows, find the function that makes the number and the function that
   makes each row; if they are two different functions, compare them on a long-gap case.
10. **Words promise more than the code.** Every switch label, help article, What's new line and button that says what
   happens ("Members get a birthday wish", "Done items leave the bell"): read the code path end to end and confirm
   it happens for EVERY member the words cover. Words wider than reality = finding (tie to the promise register).
   Include legal and privacy pages (data agreement, privacy notice, consent and sign-in screens), and check every way
   into the data, staff and direct database logins included. Every notification, link and button: follow a tap to
   where it lands; a tap that opens nothing, or a general page instead of the thing it names = finding. Every button
   that can be greyed out or do nothing: the screen says why, next to it; a disabled or silent button with no reason
   in view = finding. Every label in every language the app offers (Hinglish runs longer): check in code it can wrap
   or shrink at 320 to 390 px wide (no fixed no-wrap, no min-width that cannot shrink, no crowded top bar); text cut
   off or pushed past the screen edge = finding. Every picture the code points at (app and notification icons, badges,
   manifest and share images): is it the current brand and in the form the platform needs (size, one colour where the
   system draws only an outline)? An old-brand or wrong-form picture = finding.
   To follow taps, find the one place that handles a tapped notification and list the pages it knows; then list
   every kind of notification the code posts (on the phone and from the server) and check each kind is in that list.
   A save button greyed out because nothing changed yet counts too: the screen must say it is already saved.
   A promise that every look or change is recorded: routes that skip the app's code (the database's own login, its
   table editor, admin tools) leave no code to read, so look for a record the database itself writes (an audit
   setting, a job that pulls its logs); none = finding.

**Calibration: the audit must re-find the bugs he already found.** Before Phase B starts, a helper that has NOT seen
the fixes gets only the code at the commit BEFORE each fix and the hunts above, and must find each of these. Every one
it misses means the hunt is too weak: rewrite the hunt, then run it again.

How to run it.
C1. Coordinator, script: docs/system-map/_tools/seeds.mjs finds, for each seed, the fix commit (search commit
    messages for the R-number) and writes calibration/seeds.json {seed id, fix commit, parent commit, area
    folders the fix touched}. Seeds with no R-number are found by date and file, by the coordinator.
    seeds.json and the seed list are coordinator-only files.
C2. For each seed the coordinator makes a read-only copy of the area folders at the PARENT commit into
    _work/calib/<seed id>/ (git archive of those folders only; removed after scoring). No docs/ folder in it.
C3. A helper gets: that folder, the full text of the 10 hunts WITHOUT the seed list and WITHOUT the
    "seed pairs" line, and one sentence: "Run every hunt on this area and list every gap." It is not told
    what to look for, how many gaps exist, or that this is a calibration. It may not run git or open docs/.
    3 seeds per helper, areas mixed.
C4. Score by the coordinator: found / partly / missed per seed, in calibration/RESULT.md.
C5. A missed seed: rewrite that hunt's text, re-run ONLY that seed with a fresh helper. At most 2 re-runs
    per seed. Still missed = written in the report as "this audit cannot find this kind of bug: <why>",
    and that kind is added to the device checks only he can do.
C6. Device-only seeds (R-590 silent on OPPO, R-575 watch update notice): pass = the helper flags the code
    path as "cannot be proven in the cloud, needs a real-phone check", not "found the bug". Seed list (extend it with every bug he
reported in docs/CLAUDE-NOTES.md in the last 60 days, read the R-notes, not summaries):
- R-604: the 11:00 push counted alerts he had already handled (done lived only in the browser).
- 16 Nov: AI ideas suggested birthday wishes while automatic birthday wishes were on.
- 16 Nov: automatic birthday wish silently skipped a member whose app was not linked; no record anywhere.
- 16 Nov: he could not tell the new bell was only on main and not live.
- R-593: Today kept items already handled; a member who joined today counted as "not seen".
- R-603 / R-605: alerts showed the old icon; the badge drew as a white square.
- R-583: tapping a gym reply notification opened nothing.
- R-590: gym messages silent on his OPPO phone.
- R-575: "Your watch app has an update" never showed.
- R-581: new-feature dots on a first install.
- R-584: "Save timings" looked broken on a phone.
- 15 Nov: data agreement promised every look is recorded, but a direct read had no record; the phone form said the
  number is not kept, but the app kept it.

- (coordinator-only, hunt 1) Seed pairs to prove the hunt works: auto birthday switch -> AI ideas + Today birthday nudge; auto plan-end reminder -> "plans ending" ideas; a member who left -> every list, count and message; Pro off -> every Pro screen and help article.
The end-of-audit report lists each seed bug and which hunt or lens found it. A seed no hunt finds blocks "audit done".
