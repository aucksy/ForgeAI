round and one yes for the batch; tests, build, review, proof and delivery for every family). Batch: FIX-PLAN B02,

Families (G0): A-01, A-07, C-07, D-21, B-03 (master M02, "Privacy promises vs real data flows"), A-12 and C-74

## 1. The problem, in the user's words

"MettleUp's privacy notice and screens tell me where my data goes. Some of those sentences are not true."

Examples, all from the audit (findings.jsonl):
- A gym owner's spoken request to the AI Assistant can go to Sarvam. The notice never names Sarvam (S1).
- The notice says trainers see 30 workouts from 3 months. The app now sends a year.
- The notice says what you log stays on your phone. Android's own backup copies it to your Google account.
- Phone sign-in says "we never message you". MettleUp's WhatsApp number writes back after the check.
- The websites say they send nothing out. Every page loads its letters (fonts) from Google.
- The notice says member data is kept in India. The nightly copy sits with Cloudflare outside that promise.
- The website says our staff cannot open a member list unless the gym lets them. HQ has an emergency button.
- Door punches from entry machines are kept for ever, and the notice does not mention them.
- The store listing and member website still promise "Back up to Google Drive", which the app no longer offers.
- 31 privacy promises on screens are true today, but no test would notice when a change breaks them.

The cause is one thing: every privacy sentence is typed by hand, in many files, and nothing compares it with
what the code really sends and keeps. Each new feature quietly makes some sentence false.

## 2. The family (G0)

Searched: findings.jsonl rows whose root_cause_key is one of the seven sub-families; then the code for the same
pattern (privacy-type phrases typed outside the notice: "never sent", "not kept", "only on this phone", "stays on
this phone", "we never message", "only this gym sees", "kept in India", "nothing is uploaded"; and outbound hosts
in code that the notice does not name). Every surface: apps/mobile, the watch, apps/dashboard (panel and public
websites), deploy/hq, deploy/panel workers, supabase. The sibling list is the 91 findings plus the extra
phrase and host hits the slice A checks print on their first run (they become the starting allow-list, each
row with a reason, and every row is a finding to clear in slice B).

The guard for the whole family: **one data-flow list**, and three checks that fail CI when a sentence or a host
drifts from it (section 9).

## 3. What users see after the change

### 3a. Members, gym owners and website visitors
- The privacy notice (English and Hindi) names every outside company that gets data, for what, and how long it is
  kept. Each section reads from the data-flow list, so it is complete. Sarvam, Google (fonts, the HQ reply
  helper, Android backup), GitHub (exercise films), Hevy (routine links) and the payment company for MettleUp
  plans are named where they apply, or the flow is removed (HIM questions 1-7 decide which).
- Screen sentences say only what is true for that member: a gym member is not told "your workouts are only on
  this phone"; phone sign-in does not say "we never message you"; Delete my account says what the gym keeps.
- When the notice changes, members see one line once in the app ("We updated the privacy notice") with a link,
  and owners see it in the admin app's What's new. No silent changes.
- The store listing, member website and owner website no longer promise things the app does not do (Drive
  backup, "free with no limit" while a paid plan waits, reminders not built yet).
- Settings → About shows "Privacy notice" and "Terms" (built in R-630; R-631 only links them from the new
  promise words).

### 3b. Must NOT see
- A privacy sentence on any screen, page or store listing that a code change has made false (CI fails first).
- A company that receives data but is not in the notice.
- "Stays on this phone" or "never sent" on a screen while a switch the member turned on sends that data.
- A notice change that no member or owner is told about.
- Any new wording live before his yes (HIM question 9).

## 8. Risks and the pre-mortem
- The list itself drifts. Answer: it is checked from both sides (code hosts → list; list → notice), and a new
  outbound host or a new personal table fails CI until listed.
- The phrase check flags honest sentences ("only on this phone" for a member with backup off). Answer: such
  sentences come from the registry with the condition they depend on (9c); the screen shows the variant for
  the member's real state.
- Too big to finish. Answer: four slices, each shippable alone; A adds checks with a starting allow-list, so CI
  is green from day one and the list only shrinks.
- Wording waits on him and blocks code. Answer: slices A, C, D need no new words live; B waits for HIM 9 alone.
- The Hindi notice falls behind. Answer: 9b reads both languages.

## 9. Tests (G3)
Written before each slice's build, from this note:
- 9a. Code → list: a test lists outbound hosts in app, worker and server code (fetch URLs, SDK hosts) and personal
  tables in supabase migrations; each must be in docs/legal/data-flows.json, or in the allow-list with a reason.
- 9b. List → notice: every flow and company in the list is named in its notice section, in English AND Hindi
  (a `data-flow="<id>"` marker on the sentence); every company the notice names is in the list.
- 9c. Screen words: privacy-type phrases in app and website strings appear only through the promise registry;
  each registry promise names the flows it depends on, and a promise that says "stays on this phone" cannot cite a
  flow that leaves the phone while its switch is on.
- 9d. Proof: each registry promise names at least one test that proves it (B-03's 31 findings each become one
  such test); a promise with no existing test file fails.
- 9e. Claims (A-12, C-74): each product claim on the websites and store listing names a feature id in
  docs/system-map/features.json; a claim on a feature that is not live fails.
- 9f. Notice change: changing the notice version without a "notice updated" entry for both apps fails.
- Every new sentence: through the member-words skill, then his yes (HIM 9).

## Glossary
- Data flow: one kind of data going from one place to another (for example "a gym owner's voice request goes to
  Sarvam"), with who sees it and how long it is kept.
- Allow-list: the starting list of known gaps, each with a reason, so the new check passes today and every later
  fix removes a row.
- Promise registry: one file per app holding every privacy sentence a screen may show, with what it depends on.
